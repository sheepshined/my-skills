# Accept Agent Deliverables

## 核心原则

验收是基于**当前交付物和当轮证据**的独立判断，不是复述实现者结论。默认只读：先出具发现、证据和结论；修复与复验分开进行。

## 1. 锁定验收对象

开始前确定：

- 需求来源：用户原话、计划、验收剧本或需求清单。
- 交付范围：具体 commit、diff、文件、服务或产物。
- 保护边界：明确不能改变的架构、数据和外部系统。
- 验证环境：实际依赖、配置、模型、数据集与可用工具。

缺少任何一项时继续收集可取得的信息，并把无法覆盖的部分标为“未验证”。不得用旧文档或记忆代替当前实现。

## 2. 建立需求—证据矩阵

逐条需求指定可观察结果和证明方式：

| 需求 | 可观察判据 | 所需证据 | 结果 |
|---|---|---|---|
| 用户可完成某流程 | 主路径与关键边界均达到最终状态 | 真实操作轨迹、状态与产物 | 待验 |
| 某缺陷已修复 | 原始复现路径不再出现症状 | 同路径复测 + 回归测试 | 待验 |
| 某能力未越界 | 未授权路径零副作用 | 负样本、权限与数据检查 | 待验 |

一条需求不能只靠“代码存在”“测试曾经通过”或“最终回答看起来正确”关闭。

## 3. 按证据强度验收

按任务适用性执行，不必为纯文档产物强行跑服务：

1. **范围审查**：核对 diff 与交付范围，发现未声明改动、生成物、凭据或个人数据。
2. **自动化证据**：当轮运行相关测试与构建，记录命令、退出码和统计。
3. **行为证据**：沿用户主路径和关键边界操作，检查最终状态而非仅检查提示文案。
4. **Agent 证据**：按 `references/agent-checklist.md` 检查轨迹、配对、副作用、权限、恢复与负样本。
5. **浏览器证据**：动态页面先等待渲染并检查 DOM，再选择定位器操作；同时检查控制台、网络、截图和横向溢出。
6. **指标证据**：性能或质量提升必须保留同口径基线、数据集、环境和复测结果。

作者报告、子代理总结和历史测试只能作为线索。关键结论必须亲自核验或明确标为间接证据。

## 4. 分离缺陷与缺证

- **缺陷**：已有证据证明行为违背需求或契约。
- **缺证**：尚无足够证据判断，不得直接写成“通过”，也不得无依据断言“有 Bug”。
- **推测**：可以指导下一步测试，但不能进入最终事实结论。

每个问题给出：严重度、复现步骤、实际结果、预期结果、证据位置和最小影响范围。

## 5. 统一严重度与结论

| 级别 | 判定 |
|---|---|
| P0 | 数据丢失、越权、未批准副作用、核心流程不可用或严重安全问题；阻断交付 |
| P1 | 明确需求未满足、关键回归、核心路径缺证或恢复/异常契约失败；修复并复验后交付 |
| P2 | 不阻断核心闭环的体验、展示或维护性问题；可记录后处理 |

结论只能使用：

- **通过**：范围内需求均有有效证据，且无未解决 P0/P1。
- **有条件通过**：核心需求已证实，仅剩明确 P2；列出限制与后续项。
- **不通过**：存在 P0/P1 缺陷。
- **无法验收**：环境、对象或关键证据不足，尚不能判断通过与否。

不得用“基本通过”“应该没问题”模糊结论。

## 6. 输出验收报告

```text
验收结论：通过 / 有条件通过 / 不通过 / 无法验收
验收范围：对象、需求来源、未覆盖范围

需求—证据：
- [需求] 结果；证据；备注

发现：
- [P级别] 现象；实际/预期；复现与证据

验证记录：
- 命令或操作 → 真实输出/轨迹

边界：
- 未验证项、环境限制、仍需人工判断的事项
```

若随后修复问题，创建新的复验轮次。只复验修复项和受影响回归范围，并保留此前发现，不把旧“通过”结论自动延续到新改动。
