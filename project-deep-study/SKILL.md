# Project Deep Study（项目深度学习引导）

帮用户吃透一个代码库。不是替用户读代码，而是把"怎么学"整理成写进文档的学习手册 + 一组可验证的动手实验，之后由你基于读透的代码持续答疑。

## 核心原则

1. **文档必须对照代码核实**。引导文档几乎总是滞后于代码：过时的数字（题量/接口数）、失效的行号、已删除的模块。每个要写进或保留在文档里的事实性论断，都先用 grep / 实测验证；发现错误当场修正并在最终汇报里列出"核实与修正清单"。
2. **结论锚定 file:line**。所有"学什么"的引用都给精确文件与行号——行号是学习文档的坐标系，用户要能点开就看到目标代码。写完后精读清单的行号逐条核对，正文其余引用抽查 3 处。
3. **广度外包给探索代理，深度自己读**。目录树、行数统计、多份根文档的新旧取舍、依赖清单、数据文件格式这类"看结论就够"的调查，派 Explore 子代理并行做，保持主上下文干净；核心引擎文件（状态机/主流程/检索/数据层）必须自己逐段读透——你要靠它们回答用户后续的所有问题，这一步不能省也不能只读摘要。
4. **"怎么学"比"是什么"重要**。学习手册的价值在分阶段路线、每阶段的"通关检验"问题、可回滚的动手实验。只罗列架构描述的不叫学习手册，叫 README 复读。
5. **实验必须可回滚**。所有实验只改工作区、不提交，标注具体回滚命令（如 `git checkout -- <file>` 或还原哪个常量）。
6. **先定位入口文档再动手**。用户指定了入口文档（如 `PROJECT_GUIDE_AND_REVIEW.md`）就用它；没指定时先看根目录 `ls *.md` 并各读前 30 行，判断哪份反映现状、哪些是历史档案，确实无法判断再问用户一句。项目没有任何引导文档时，按手册模板新建一份。
7. **语言跟随用户**（本技能源自中文学习场景，默认中文写作）。

## 工作流程

### Phase 0 盘点现状

1. 通读用户指定的入口文档（或上一步选出的现状文档），记住它声称的结构与事实清单——后面要逐条核实。
2. 派一个 Explore 子代理（只读）做广度侦察，一次问齐：
   - 根目录各 .md 的定位与新旧（哪些反映现状、哪些是历史档案、哪些与入口文档重复）；
   - `git log` 近期提交主题 + `git diff` 未提交改动的实质内容（文档更新之后发生的改动最关键）；
   - 依赖清单要点（requirements.txt / package.json / .env.example）；
   - 关键数据文件格式（题库/配置/种子数据的字段结构）。
   若当前环境没有 Explore 类子代理，就自己用 Grep/Glob/Read 完成这四项侦察，命令总数控制在 10 条以内，不要陷入逐文件精读。
3. 自己做结构普查（快命令即可）：目录树（排除 node_modules/.venv/.git/__pycache__/.pytest_cache/dist 等缓存与产物目录，它们常导致 find 报错）、`wc -l` 排出核心文件、"入口面"清单。入口面按项目类型替换：Web 服务 grep 路由装饰器（`@app` / `@router` / 路由表）；CLI 看 argparse/click 子命令注册；纯库看 `__init__.py` 公开导出；管线/编排看 main 入口与任务注册表。

### Phase 1 深度精读核心引擎

- 找到项目的"主线"（一次请求的生命周期 / 一条消息的处理链 / 一个任务的状态机），沿主线把核心文件读全。典型顺序：状态定义 → 流程编排引擎 → LLM/IO 链层 → 检索/数据层 → 服务入口的驱动段。
- 边读边记录"精读候选清单"：每处写清 行号、它解决什么问题、值得学的机制（设计取舍、容错兜底、防错注释）。
- 配置层（config/env）单独过一遍：所有可调参数是后面"动手实验"的素材库。

### Phase 2 核实入口文档

对照代码逐条核实文档中的事实性论断。重点核：

- 数量类：题目数/接口数/测试数/文件行数（用 grep -c、实测接口数，不要信文档抄文档）；
- 位置类：文档引用的文件是否都存在、关键函数行号；
- 行为类：文档描述的关键机制与代码是否一致（挑最核心的 3~5 个机制核对）；
- 记录"修正清单"：错误项、改成了什么、依据。

### Phase 3 增补学习手册

读 [references/handbook-template.md](references/handbook-template.md)（手册结构与每节写作要求，动手写之前必读），然后动笔。落笔位置按阈值决策：

- 入口文档存在且 ≤800 行、编号体系可容纳新章节 → **追加新章节**（沿用其编号；其用"八、"则子节为 8.1~8.7，其用"Part n"或无编号则本章子节用 X.1~X.7 并在章首注明；若原文档已有引言，省去 X.0 避免重复）；
- 入口文档 >800 行，或结构塞不下 → 新建 `LEARNING_GUIDE.md`，在入口文档头部加一行交叉引用，阅读路径表写在新文件头部；
- 无入口文档 → 新建 `LEARNING_GUIDE.md`，按模板先补"定位与技术栈 + 目录职责"再写学习手册。

写作红线：不重写文档中已正确的内容；每个引用都带 file:line；通关检验问题必须能从代码里找到答案（考理解不考记忆）；实验与概念一一对应。

### Phase 4 沉淀与汇报

1. 若当前环境有持久记忆机制（系统提示中给出记忆目录、或存在 memory/MEMORY.md 索引），写入或更新一条 project 记忆：项目路径、用户学习目标、学习手册所在章节（作为后续答疑索引）。检测不到就跳过，不要为此创建目录结构以外的猜测性写入。
2. 最终汇报必须包含：核实与修正清单（文档哪里错了、改成了什么）、手册新增了什么（章节结构一览）、**建议的入手点**（从哪一阶段哪几个文件开始，一句话理由）、以及 2~3 个可以马上做的实验。

## 快慢两档（必写范围的唯一口径）

- **快档**（核心代码 <3k 行，或用户只要快速 orientation）：侦察可省略子代理改为自读；精读压缩到主线 3~5 个文件；手册必写三节——概念地图、学习路线、实验（精读清单/FAQ/调试速查可并进对应节或省略）。预算 1~2 天。
- **慢档**（大项目或用户要深入）：全程照做，手册七节全写（精读清单可扩到 20+ 段，可为前后端各写一条路线）。中型项目预算 4~6 天，大型项目 6~10 天。
- 完成标准按档位对号：快档只要求三节齐全，慢档要求全部。

## 完成标准

- [ ] 入口文档的事实论断全部核实过，修正项已落盘并汇报
- [ ] 手册含当档必写小节（快档三节 / 慢档七节），所有引用带 file:line
- [ ] 实验均标注回滚方式（已跟踪文件 `git checkout -- <file>`；实验新建的文件直接删除；非 git 项目把原值抄进实验说明里）
- [ ] 用户知道从哪里开始、第一步做什么
