## 1. 概念边界

官方对比（2026-03-05 *Skills explained*）给出的定位：

| 概念 | 定位 | 生命周期 | 一句话判据 |
|---|---|---|---|
| Skills | 程序性知识 | 跨会话复用 | 教模型**怎么做**某类事 |
| Prompts | 单次即时指令 | 一次性 | 这一次我要什么 |
| Projects | 项目内背景知识 | 项目内 | 这个项目的背景是什么 |
| Subagents | 任务委派（独立上下文 + 独立工具权限） | 单次委派 | 把事**交给别人**做，且只给他该有的权限 |
| MCP | 工具连通性 | 常驻 | 让模型**够得着**某个外部系统 |

官方原话（2025-12-19 *Skills + MCP*）：

> "If you're explaining how to do something, that's a skill. If you need Claude to access something, that's MCP."

记忆钩子：**Skill 是说明书，MCP 是数据线与电源，Tool 是插件本身，Subagent 是外包团队。**

**注意**：官方**没有**把 Skill 与 tool / function calling 做正面比较的原文。安全表述是——function calling 解决"模型如何表达一次调用请求"，tool 是"可被调用的能力单元"，Skill 是"调用这些能力时的作业指导书"：前者是机制，后者是知识。不要把它说成官方结论。

## 2. 技能拆分原则

- **按"动作"拆，优于按"品类"拆**。动作与复用性对齐（写文案、做图、选品、投放、复盘），品类差异放进 `assets/` 与 `metadata`，避免为 5 个品类复制 5 套技能。
- **先窄后合并**：先做边界清晰的窄技能，等出现稳定重复再合并。
- **同名职责不重叠**：两个技能若职责相近，它们的 `description` 会互相争抢路由，必须合并或明确划界。
- 复杂度判据：一个技能若需要 3 个以上互不相关的判断分支，通常该拆成两个。

## 3. Agent 协同三形态

| 形态 | 说明 | 适用场景 |
|---|---|---|
| 单 Agent + 技能库 | 一个 Agent，按 `description` 路由到不同 Skill | 技能数量 < 数十、任务边界模糊 |
| 编排者 + 专家 Agent | 上层编排器拆解任务，分派给各自持有 bundle 的专家 Agent | 需要多角色、权限需隔离 |
| 工作流为主 + 技能为辅 | 主干是确定性工作流，技能只负责其中的判断与生成环节 | 合规、财务、价格等不能有幻觉的环节 |

**判断句**：步骤确定 → 工作流；需要判断但不需自主决策 → Agent + 技能库；需要自主拆解与委派 → 编排者 + 专家 Agent。

## 4. 规模与路由

官方一条反直觉但实用的经验：**元数据会互相争抢模型的注意力**。

- 技能数上升后路由准确率**先平后降**，必须用评测测召回，不能靠感觉。
- 停止判据很直接：**"性能开始下降，就停止添加。"**
- 扩张策略：按角色做 bundle（内容运营包、投放包、数据分析包），不要把所有技能平铺给所有 Agent。

## 5. 权限与数据边界

三种可用手段（官方企业实践页）：

1. **`allowed-tools` 显式声明**：技能只被预授权它能用的工具（标注 Experimental，但方向明确）。
2. **`context: fork` / subagent 隔离**：高风险动作放在独立上下文的子智能体里执行，主流程不直接持权。
3. **版本控制 + 校验**：技能纳入 Git，用签名/校验和验证，**生产环境 pin 到具体版本**。

再往上一层是产品级要求：**数据分级与最小必要授权**。让技能能读店铺经营数据，就必须回答——读哪些字段、用在哪个环节、留存多久、谁能导出。

## 6. 生命周期与 registry

生命周期：`plan → create & review → test → deploy → monitor → iterate / deprecate`。

两条治理原则：

- **作者与评审职责分离**：写技能的人不给自己发许可证。
- **安全审查清单**逐项过：代码执行、指令操纵（prompt injection）、MCP 引用、网络访问、硬编码凭证、文件系统访问范围。

内部 registry 建议字段：`purpose`（用途）、`owner`（负责人）、`version`（版本）、`dependencies`（依赖）、`eval`（评测结果）。它回答"谁在用什么、改了会不会连带炸掉别的"。

## 7. 反模式清单

| 反模式 | 后果 |
|---|---|
| 为模型已掌握的知识建技能 | 白占 L1 注意力与 L2 预算 |
| 触发词只写在正文里 | 路由看不到，技能永不触发 |
| `references/` 一层套一层 | 模型读两层就放弃 |
| 一个巨型 `SKILL.md` 塞全部内容 | 触发一次就吃掉大量上下文 |
| 技能里写 `pip install` 或访问外网 | 在无网络 surface 直接失败 |
| 复制已有技能改名 | 两份 `description` 互相争抢路由 |
