# 参考：评测与验收

> 用于设计技能评测用例、给技能定验收标准、判断"体系是否在退化"。

## 1. 评估驱动开发五步（官方 best-practices）

顺序不能反——先找缺口，再写技能：

1. **先不用 Skill，跑代表性任务**：记录模型在哪一步卡住、哪一步做错。
2. **挑 3 个评测场景**：把暴露的缺口固化成 3 个可重复的场景。
3. **建立基线**：记录无 Skill 时的表现作为对照。
4. **写最小指令**：只写针对缺口的那几句。
5. **迭代**：每加一段说明就回跑评测，能提升才留下。

**核心原则**：Skill 是"补差"用的，不是"把我知道的都写上"。模型已经会的内容写进去，只会浪费 L2 预算并稀释真正的指令。

## 2. 评估维度（官方 enterprise 页列举）

- **触发准确率**：该触发时触发，不该触发时不触发
- **隔离性**：技能互不干扰（触发 A 不会顺带污染 B）
- **共存性**：多个技能同时在场时路由是否仍然选得对
- **指令遵循**：正文里的步骤是否被真的执行
- **输出质量**：结果本身是否达标

## 3. 每个技能必须提交的 3–5 条查询

官方硬要求：每技能 3–5 条代表性查询，且必须覆盖三类边界：

| 类型 | 作用 | 写法要点 |
|---|---|---|
| 应触发 | 确认正常路径可用 | 用真实用户的自然说法，不要用技能名硬凑 |
| 不应触发 | **最重要**——线上最典型的故障是被用在不该用的地方 | 选相邻但不同类的请求（如"问弱项趋势"vs"读单份报告全文"） |
| 模糊边界 | 最容易误触发的那一类 | 刻意去掉关键限定词，看路由是否仍能选对 |

并且必须**在所有目标模型档位上分别测试**（官方点名 Haiku / Sonnet / Opus）——小模型通过不代表大模型不误触发，反之亦然。

## 4. 三类评测与工程实现的对应

工程上把评测分三类，与助手工具治理是同一套思路：

| 类型 | 断言什么 | 技能场景下的例子 |
|---|---|---|
| routing（路由） | 该走哪条路径，不该走哪条 | 问弱项趋势时应触发趋势技能，而不是逐份读报告 |
| contract（契约） | 返回结构、权限、隔离 | 技能声明的 `allowed-tools` 与实际调用一致；用户数据不跨用户可见 |
| trajectory（轨迹） | 多轮状态与中断恢复 | 多技能共存时的执行顺序、批准/拒绝/恢复是否稳定 |

**指标**：除通过率外，单独记录**误触发率**（不应触发用例中被触发的比例）。技能扩编时，误触发率是先坏的指标。

## 5. 扩编看门指标

官方经验：元数据会互相争抢注意力，路由准确率会**先平后降**。

- 每新增一批技能，回跑全量评测，比对触发准确率与误触发率。
- **判据**：性能开始下降，就停止添加；先做窄技能，需要时再合并。
- 按角色/场景做 bundle，而不是把所有技能平铺给所有 Agent。

## 6. 验收清单（逐项勾）

- [ ] 每个技能有 3–5 条评测查询，含至少 1 条不应触发、1 条模糊边界
- [ ] `description` 自包含（做什么 + 何时用 + 不用于什么），第三人称
- [ ] 所有技能名的职责互不重叠，无两个 `description` 争抢同一类请求
- [ ] `SKILL.md` 远低于 500 行，长内容在 `references/` 且只引用一层深
- [ ] 引用的 `references/`、`assets/` 文件都真实存在
- [ ] 脆弱步骤已改为 `scripts/` 脚本，而非自然语言描述
- [ ] 技能不含网络依赖或安装步骤（除非该 surface 明确支持）
- [ ] 明确的数据边界：读哪些数据、调哪些工具、客户/用户之间如何隔离
- [ ] 技能纳入版本控制，生产环境 pin 版本
