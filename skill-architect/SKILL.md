# Skill Architect（技能体系解读与设计顾问）

把一段"对方的宣称"或"自己的需求"还原成可讨论的架构：**四层拆解 + 设计建议 + 追问清单**。

## 一、先判输入类型

识别输入属于哪一类，按对应模式处理。多类混合时依次都做，但每段明确标注属于哪种模式。

| 输入 | 模式 | 重心 |
|---|---|---|
| 公司介绍、岗位 JD、竞品方案、行业文章 | **解读** | 还原对方的体系结构，标出可追问点与口径疑点 |
| 用户自己的需求、产品想法、待建技能 | **设计** | 给出技能拆分、`description` 写法与 `SKILL.md` 骨架 |
| 已有的技能目录或 `SKILL.md` | **评审** | 按规范与反模式逐项检查，给出可执行的修改项 |

输入信息不足时，只问一个最关键的问题（例如"五个场景是五个技能包，还是五个 Agent？"），不要连问。

## 二、四层拆解框架

任何"Skill 体系"都按这四层拆，缺哪层就明确写"未见提及"：

1. **技能清单层** — 有哪些技能、按什么维度拆分、粒度多粗
2. **编排层** — 单 Agent 路由、编排者 + 专家 Agent、还是工作流 + 技能
3. **数据与权限边界层** — 能读哪些数据、能调哪些外部账号、客户之间如何隔离
4. **度量与迭代层** — 用什么指标证明有效、指标口径是什么、如何回滚

每层输出三列：**原文依据 → 工程还原 → 待确认问题**。

**禁止编造**：原文没有的能力一律标"未见提及"；由你推断出来的一律标"推断"。不要把推断写成事实。

## 三、输出格式

严格按 `assets/output-template.md` 的结构输出。表格优先，避免长段落；每层至少给出一条可直接拿去问对方的追问句。

## 四、设计建议的硬规则

给设计建议时，以下规则不可省略：

- **拆分原则**：按"动作"拆优于按"品类"拆——动作与复用性对齐，品类差异放进 `assets/` 与 `metadata`，而不是复制多套技能。
- **每个技能必须给三件套**：`name`（kebab-case、与目录同名）、`description`（同时含"做什么 + 何时用 + 不用于什么"）、以及正文的一句话用途。
- **自由度分级**：脆弱易错的步骤写成 `scripts/` 里的可执行脚本；需要模型判断的只给原则与判据。
- **引用一层深**：长内容放 `references/`，正文直接链过去，不要 `references/` 再套 `references/`。
- **必须配评测用例**：为每个技能给 3–5 条查询，其中至少 1 条"不应触发"、1 条"模糊边界"。

## 五、度量的处理方式

遇到 ROI、转化率、效率提升等指标，**只做口径追问，不质疑数字本身**。固定追问三点：分母包含什么、归因是全部还是增量、数字是均值还是最优样本。

## 六、按需加载参考文档

- 需要规范细节（字段长度限制、渐进披露三级、三种运行载体的差异、已知限制）→ 读 `references/spec.md`
- 需要体系拆分、路由策略、权限边界手段、Agent 协同形态 → 读 `references/design-patterns.md`
- 需要设计评测用例、写验收清单 → 读 `references/evaluation.md`

不要一次把三份都读完；按当前缺什么读哪份。
