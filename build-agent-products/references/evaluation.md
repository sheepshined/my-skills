# Agent 调试与评测契约

## 一、先根因，后修复

收到“闪屏、卡住、不能用、行为不对”等短消息时，把它当作待排查现象：

1. **保留现场**：读取完整错误、堆栈、控制台、网络请求、进程与最近变更。
2. **稳定复现**：记录环境、命令、输入、步骤、频率和实际输出。
3. **沿边界取证**：检查每个组件的输入、输出、配置和状态，定位首先偏离契约的位置。
4. **对照工作路径**：寻找仓库内相似但正常的实现，列出真实差异。
5. **提出单一假设**：写成“因为证据 X，所以怀疑 Y”，再用最小实验验证。
6. **只改一个根因**：不顺手叠加多个修复；失败后回到证据，不继续堆补丁。
7. **回归原始症状**：用同一复现路径确认消失，再跑相关回归。

证据不足时明确区分“已证实事实 / 当前推测 / 下一步验证”。不得把“环境跑不了”“依赖要联网”“性能瓶颈就是 X”等推测写成事实。

## 二、按不变量设计测试

| 层 | 必测内容 |
|---|---|
| 状态机 | 路由、终止、恢复、重放、非法 phase、重复输入 |
| 工具协议 | 参数校验、未知工具、异常、超时、结果截断、tool call 配对 |
| 权限与副作用 | 批准、拒绝、重复确认、参数变化、越权、零副作用路径 |
| 数据 | 用户隔离、事务、版本冲突、迁移、幂等、删除与恢复 |
| RAG | 命中、无结果、低相关、原文引用、索引同步、负样本 |
| 前端 | 主路径、空态、加载、错误、刷新、重连、移动端、控制台 |
| 可观测 | 轨迹能关联用户、会话、工具、状态与副作用，不泄露秘密 |

优先把事故转化为确定性契约测试。模型输出可变化，但权限、状态、配对、隔离和副作用必须稳定。

## 三、建立真实 LLM 评测

每个 Agent 或 Skill 至少覆盖三类用例：

- **应触发**：应选某工具、技能或流程。
- **不应触发**：相似表达但不能进入该流程，记录误触发。
- **模糊边界**：允许多条合理路径，但禁止越权或进入无关流程。

每条用例尽量声明：

```text
input + context
expected_tools / forbidden_tools
expected_skills / forbidden_skills
state_assert / side_effect_assert
max_calls / max_activations
manual_rubric（仅用于确实需要人工判断的质量）
```

判据优先使用状态与轨迹断言，再使用精确字段、必要内容，最后才是 rubric。安全与主观质量用例可标 `pending_review`，不得自动算作通过。

保留数据集版本、模型、提示词、参数、时间和原始轨迹。单次失败要保留此前结果；费用不足、网络失败和框架异常标为未完成，不伪装成模型质量结论。

## 四、性能与优化

1. 先测基线并固定口径：P50/P95、首字延迟、总时延、token、成本、内存或首屏体积。
2. 用 profile、构建产物或调用轨迹找瓶颈。
3. 一次只改一个主要变量。
4. 用同一环境、同一数据集复测。
5. 同时检查质量与功能回归，避免只快不准。

报告格式：`指标：基线 → 结果（变化），环境/数据集/命令`。没有基线就只报告当前实测值，不写提升比例。

## 五、完成声明门禁

| 要说的话 | 至少需要 |
|---|---|
| “测试通过” | 当轮完整命令、退出码和统计 |
| “Bug 已修复” | 原始症状复现路径通过 + 回归测试 |
| “前端可用” | 真实浏览器主路径与相关边界路径 |
| “Agent 路由正确” | 实际工具/技能轨迹 + 正负例 |
| “更安全” | 具体攻击或越权用例前后对照 |
| “性能提升 X%” | 同口径基线与复测结果 |
| “需求全部完成” | 逐条需求—证据映射，无遗漏项 |

最终汇报把 `passed / failed / skipped / pending_review / not_run` 分开。验证范围之外的能力明确保留为未验证。
