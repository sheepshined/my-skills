# Agent 项目作品集与 FDE 表达

## 一、先建证据清单

从代码、测试、评测和演示中提取四类证据：

1. **问题证据**：谁在什么场景遇到什么成本或失败。
2. **机制证据**：状态图、工具契约、权限门、检索链、恢复机制、数据隔离。
3. **质量证据**：测试数量与范围、真实轨迹、性能基线、评测集口径。
4. **结果证据**：可复现的功能闭环、实测指标、真实用户或部署事实。

把每项标为 `已验证 / 有代码但未实测 / 仅设计 / 未实现`。简历与答辩只把前两类写成已具备能力，不用计划书冒充交付。

## 二、项目描述采用“机制—证据—价值”

每条项目bullet优先包含：

```text
动作 + 具体机制 + 解决的工程事故或用户问题 + 可核验证据
```

示例：

> 设计 LangGraph 人在回路面试状态机，将准备副作用与等待输入拆分为独立节点，避免恢复时重复出题，并用状态轨迹测试覆盖追问与报告恢复。

> 构建 BM25 与向量双路召回及 RRF 融合，使用固定探针评估 Hit@5/MRR；对外仅填写同数据集复测得到的实际数值。

> 为 Agent 写操作增加提案—确认与参数指纹审批，覆盖拒绝、重复确认和越权路径，确保未批准操作零副作用。

不要照抄示例中的能力；先用当前项目证据核实。不要为了量化而编造延迟、准确率、用户数、覆盖率或生产流量。

## 三、GitHub 展示顺序

主 README 优先让访客快速回答：

1. 解决什么问题，适合谁。
2. 30 秒演示：截图、GIF 或视频。
3. 核心闭环与架构图。
4. 三项真正有辨识度的机制，不堆技术 logo。
5. 如何启动与最小演示账号。
6. 测试、评测与指标口径。
7. 当前边界和明确不做什么。

根目录只保留主要入口文档，历史方案与交接资料归入文档目录。生成缓存、数据库、个人数据、密钥和临时报告不得进入仓库。

早期原型可保留，但标注与主项目的关系；主项目不要同时呈现多个互相矛盾的前端、启动命令或测试数字。

## 四、答辩与面试讲解顺序

用一条真实用户链路串起项目：

```text
用户问题 → 为什么普通 LLM 调用不够 → 自主性为何放在这一层
→ 核心状态/工具/检索契约 → 最棘手失败 → 如何定位与修复
→ 如何用测试和评测证明 → 当前边界 → 下一步取舍
```

被问到“为什么不用多 Agent / 某新框架”时，给出任务判据和迁移成本，不回答“因为项目没用”。被问到不知道的数据时，直接说未测，并说明如何测。

## 五、FDE 视角补充

面向交付或前沿部署场景，除模型能力外说明：

- 客户环境与数据边界。
- 现有系统如何接入，哪些内核不能改。
- 权限、审批、审计和失败回滚。
- 离线、弱网、模型不可用与成本限制。
- 验收数据集、业务口径和上线后的观测。
- 哪些是 Demo 能力，哪些达到可部署条件。

没有真实部署、运维和多用户证据时，写“本地可运行产品原型”或“具备端到端闭环”，不要直接宣称“生产级系统”。
