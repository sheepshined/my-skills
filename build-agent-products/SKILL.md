# Build Agent Products

## 核心原则

把自主性放在确实需要动态决策的层，把事实、状态、权限、副作用和完成声明变成可验证契约。先复用已经跑通的机制，再引入新框架；先取得证据，再解释根因或宣称完成。

## 1. 建立事实底座

开始设计或修改前：

1. 读取当前项目的 README、计划书、交接文档、目录树和相关源码，确认哪份文档代表现状。
2. 把记忆、历史对话和旧文档当作线索，用当前代码、配置或实测复核；冲突时以当前证据为准。
3. 写清四项：**目标、非目标、受保护边界、未决决策**。不得把用户尚未拍板的产品决策悄悄变成默认实现。
4. 涉及 Agent 机制时，优先查当前仓库的等价实现和实装依赖源码；若存在 `E:\hiagent\agent-study`，再查对应 `analysis_*` 与 handbook，结论带出处。没有证据的断言标为“未验证”，同时给出验证方法。
5. 只询问会阻塞工作的决策；其余事项以可逆、最小侵入方式推进。

## 2. 选择正确任务路径

| 任务 | 必读资源 | 产出重点 |
|---|---|---|
| 新建或升级 Agent、RAG、工具、记忆、多 Agent | `references/architecture.md` | 自主性分层、边界、状态与副作用契约 |
| 修 Bug、测试失败、行为异常、性能问题 | `references/evaluation.md` | 复现、证据链、单假设、最小修复、回归 |
| 建立测试、真实 LLM 评测、验收或完成声明 | `references/evaluation.md` | 不变量、正负例、轨迹、实测结果、未验证项 |
| GitHub 包装、简历、答辩、FDE 方案表达 | `references/portfolio.md` | 机制—证据—价值，拒绝伪指标 |

同时涉及多类任务时，按“架构 → 实现 → 评测 → 表达”顺序加载，不一次读完全部资源。

## 3. 先定义契约，再写实现

在动手前明确：

- **状态 owner**：哪些字段由图、服务端、前端或用户分别拥有。
- **工具契约**：输入输出、身份来源、用户隔离、超时、错误返回和最大结果大小。
- **副作用契约**：读、写、执行分别何时发生；哪些操作必须提案、审批或二次确认。
- **恢复契约**：重试、恢复、重放、断线和刷新时，什么必须保持幂等。
- **证据契约**：回答中的数字、引用、评分与结论如何回溯到原始记录。
- **验收契约**：用什么自动化测试、真实轨迹或浏览器操作证明每条需求。

若这些契约与现有实现冲突，先指出冲突，不用新抽象掩盖它。

## 4. 以最小纵向切片落地

1. 找出一个当前仓库已经工作的相似路径，完整阅读其调用链。
2. 先打通一个可演示的端到端切片，再扩展相邻场景；不顺手重构无关模块。
3. 优先新增适配层或编排层，不重写稳定内核；越过用户指定边界时先确认。
4. 为关键不变量和失败路径写测试，不只测快乐路径。
5. 保持依赖与实装版本一致；不凭旧教程假设 API。
6. 默认不写注释。用户要求加注释时使用中文，只解释机制、不变量和非显然原因，不复述语法。
7. 不自动提交、推送、发布或执行外部可见操作；按用户当次授权范围行动。

## 5. 设置完成质量门

宣称“完成、修复、通过、提升”前，取得当轮新证据：

- 自动化测试：实际命令、退出码、通过/失败/跳过数量。
- 构建：完整构建命令成功，不用 lint 代替构建。
- Bug：按原始复现路径验证症状消失，并有回归测试。
- UI：真实浏览器走通主路径与边界路径，检查控制台和关键交互。
- Agent：检查工具轨迹、状态变化、副作用和负样本，不只看最终文案。
- 指标：保留数据集、基线、口径和结果；没有实测就不写提升百分比。

无法验证的路径明确写“未验证”，不以“应该可以”收尾。

## 6. 按固定结构交付

根据任务裁剪篇幅，但保留以下顺序：

```text
目标与边界：做了什么，明确没动什么
机制与证据：关键设计或根因，附 file:line、命令或轨迹
改动与产物：列出实际变更和交付位置
验证结果：逐项对应需求，附真实结果
边界与后续：未验证项、未决决策、真实限制
```

面向用户保持中文、直接、少客套。解释机制与取舍，不堆砌“生产级”“企业级”“完美”等无证据标签。

## 反合理化检查

| 诱惑 | 正确动作 |
|---|---|
| “这个未决项先替我默认了” | 保留未决；若必须选临时行为，显式标注并让用户可改 |
| “这个框架看起来更先进” | 先证明现有模式不足，再比较迁移成本与收益 |
| “没有日志也能判断根因” | 先取证；把推测与事实分开 |
| “测试通过就说明需求完成” | 逐条对照需求，补真实轨迹或 UI 验收 |
| “简历需要更亮的数字” | 只写可复现指标，否则写机制与工程证据 |
| “再加一个 Agent 就更智能” | 先证明任务可分解、上下文值得隔离且能独立验收 |
